# Siumora: complete functionality, speed, and UI roadmap

**Working baseline:** 30 September 2026. **Scope:** the customer storefront, Fastify API, Medusa replacement, both operator interfaces, background jobs, provider integrations, and launch operations. This is an implementation backlog, not a claim that the live site has passed acceptance. Status below is based on the repository; production credentials, live traffic, and browser measurements were not available for this audit.

## 1. Target and rules for completion

Every visible control must produce a correct result, a useful empty state, or a clear refusal. A screen is complete when its data comes from the active backend, its mutations survive reloads and retries, its permissions are enforced by the server, its errors are recoverable, and its mobile and keyboard paths pass review. A feature that works only with a development echo, courier simulation, file-local uploads, or seed data is **not live-ready**.

Use **P0** for launch or cutover blockers, **P1** for the full operator and shopping experience after the core path works, and **P2** for growth features whose triggers are in [`../TODOS.md`](../TODOS.md). Track each row below as an issue with an owner, acceptance evidence, and a link to the code change. Keep one active commerce source of truth: Fastify until the Medusa cutover gate passes, then Medusa. Do not silently fall back between them.

| Release level | Definition of done |
|---|---|
| Functional | Happy path, empty state, invalid input, timeout, retry, duplicate request, permission denial, and reload verified; price, stock, tax, and status agree across UI, API, invoice, and admin. |
| UI | Brand tokens, responsive layout at 320/390/768/1440 px, visible focus, readable validation, no hidden primary action, no horizontal overflow, and tested light/dark themes. |
| Speed | Field Core Web Vitals and route/API service levels in section 5; no performance regression in CI or the canary release. |
| Operations | Logs, trace/correlation ID, metric, alert, runbook, audit entry for sensitive writes, and a rollback or compensation path. |
| Evidence | Automated tests for critical contracts and a signed manual walkthrough on a production-like staging environment. |

## 5. Enterprise speed, reliability, and UI quality budgets

These are **proposed service objectives** until measured in staging and real-user monitoring. Record a baseline first, then assign an owner to each regression. The existing [`02-frontend.md`](02-frontend.md) asks for stricter PDP lab budgets (LCP <= 1.8 s, INP <= 200 ms, CLS <= 0.05, client JS <= 150 kB gzip); retain those as optimization targets while using the field thresholds below as the release floor. Google's [Core Web Vitals guidance](https://web.dev/articles/vitals) measures mobile and desktop at the 75th percentile; WCAG 2.2 AA is the [accessibility conformance target](https://www.w3.org/TR/WCAG22/).

| Measure | Release floor / alert | How to measure and improve |
|---|---|---|
| Field LCP, INP, CLS | p75 mobile and desktop: LCP <= 2.5 s, INP <= 200 ms, CLS <= 0.1. Alert on 7-day deterioration; keep the stricter PDP lab target. | RUM by route and device; Lighthouse CI on home, collection, PDP, bag, checkout. Compress/reserve images; prioritize only the actual LCP image; defer below-fold galleries, voice, and marketing code. |
| Route speed | p95 initial navigation <= 3 s on the agreed mid-range Android/4G profile; p95 warmed catalog navigation <= 1.5 s. | Test from India-like latency; split server timing into cache, API, DB, and image/CDN segments. These are product goals, not claims about current measurements. |
| API/DB | p95 read <= 300 ms and p95 mutation <= 800 ms at expected steady load; checkout p95 <= 2 s excluding payment-provider time. | Trace p50/p95/p99; indexes on hot catalog/order queries; bounded pagination, connection pooling, no per-row request loops, slow-query alerts. Revisit targets after load baseline. |
| Admin | p95 list/filter interaction <= 1 s after initial load for 10k records; no unbounded tables or blank load state. | Server pagination/filtering and selective projections; cache read-only rollups with explicit freshness labels. |
| Reliability | 99.9% monthly availability goal for browse and checkout endpoints, checkout creation error rate < 0.5% excluding user validation/provider declines; no duplicate charge/invoice/order. | Synthetic browse + COD + prepaid probes, provider callbacks, queue lag and dead-letter alerts, backup restore drill, incident runbook. Track payment success separately from system errors. |
| Accessibility | WCAG 2.2 AA review on all customer and operator workflows. | Automated axe checks plus manual keyboard, screen reader, zoom 200%, reduced motion, focus order, error announcements, and touch target checks. |

Use the existing Next Cache Components deliberately: cache public catalog content, invalidate product/collection tags after admin writes, and keep stock, totals, identity, and private orders fresh. Next's [Cache Components guide](https://nextjs.org/docs/app/getting-started/partial-prerendering) documents cache tagging and revalidation; verify behavior on the installed Next version. Use a CDN and appropriately sized WebP/AVIF assets for public images; never shared-cache personal pages, invoices, or checkout. Run a festival-profile load test **before** a planned campaign, including payment/provider timeouts and worker backlog.

## 7. Verification matrix and release evidence

1. **Contracts and data:** run migrations from a clean database and upgrade path; SDK contract against both transports; concurrency tests for last-unit stock, invoice number, checkout idempotency, webhook replay, COD remittance duplicate import, and refund/restock once-only behavior. Map each P0 row in [`../docs/medusa-parity-checklist.md`](../docs/medusa-parity-checklist.md) to a passing test or an explicit, dated waiver.
2. **Browser journeys:** expand Playwright beyond the current three tests: mobile navigation; collection filter/back; search empty and voice fallback; product variant/gallery/wishlist; bag quantity/merge; COD and prepaid success/failure; sign-in/guest claim/sign-out; order tracking/invoice/NDR/return; policy/contact; consent withdrawal; offline/API outage. Run desktop Chromium and at least one mobile profile; add cross-browser checks for checkout and payment modal.
3. **Admin journeys:** product publish to storefront, inventory adjustment, order state to fulfillment, NDR, return/refund, remittance import, GST export/reconciliation, settings kill switch, audit search, privacy export/erasure, role denial, second-factor recovery. Use seeded fixtures with realistic volume for list performance.
4. **Provider and operations drills:** invalid signature, late/duplicate webhook, payment success with browser closed, courier timeout, missed pickup, messaging outage, worker crash, DB restore, cache invalidation after price edit, and rollback after a Medusa canary. Record expected customer screen, operator alert, and final ledger state.
5. **Visual and accessibility sign-off:** screenshots at the four widths and both themes for all route families; keyboard and screen-reader walkthroughs; verify focus, error text, touch targets, contrast, motion preference, and overlays; compare against `brand-kit` tokens.
6. **Release report:** publish measured CWV/API/load results, unresolved defects with owners, provider/legal confirmations, reconciliation totals, rollback procedure, and a route-by-route pass sheet. No “fully functional” claim until this evidence exists.

## 8. External decisions and current limits

- **Business owner:** provide verified legal entity, GSTIN, registered address, grievance contact, support channels, approved policy wording, product claims, and imagery. Current repository placeholders must not be published as real disclosures.
- **Provider owner:** provision Razorpay, Shiprocket, WhatsApp/SMS, media storage, domain, and hosting accounts; complete KYC/templates/webhook configuration and one live low-value end-to-end test per money/shipping path.
- **Technical owner:** choose the Medusa cutover date only after parity and rollback gates. Decide whether the legacy `/admin` becomes a redirect or is retired after all its unique panels have moved.
- **Product owner:** prioritize P1 merchandising, search, reviews, recommendations, locale, and AI by real traffic/catalog triggers rather than treating every feature in the older blueprint as a launch prerequisite.

The roadmap does not estimate engineering weeks from file count. Size the issue set after phase 0 measurements and provider readiness; dependencies and external approvals can dominate calendar time.
